01

What's actually here

The backend is genuinely well-built at the level of individual resolvers. The problems are all at the seams between correct decisions.

Headline

A self-registered patient account — one public API call, no verification — can read every tenant's clinics, service catalogue with prices, products, rooms, and clinician roster. Reproduced live in this audit; the 602-test suite passes clean because it mocks the database that would have caught it. Full transcript in Security proof.

What holds

  • Fail-closed auth by default — verified live, anonymous queries reject
  • Correct, load-bearing global-guard ordering (throttle → auth → roles → IP)
  • Timing-safe login, bcrypt cost 12, Redis lockout before password check
  • Real TOTP 2FA with single-use backup codes
  • AES-256-GCM at rest for secrets, fails loudly rather than falling back to plaintext
  • Self-scoping uses fail-closed sentinels, not omitted filters
  • Real Razorpay integration — HMAC verification with timingSafeEqual

What breaks

  • Org-less callers (a category self-registration now creates on demand) read every tenant's catalogue
  • Frontend accepts a forgeable mock_-prefixed token as a full super_admin session
  • @@index count across 41 Prisma models: zero
  • 14 routed pages render fabricated data with no GraphQL call at all — 11 have a real backend already sitting unused
  • The RBAC permission matrix is stored and editable; nothing reads it to authorise anything
  • No CI pipeline exists — "verify before commit" is a convention, not a control

03

Security proof — reproduced live

Not a theoretical read of the code. A throwaway account was created against the running backend and used to probe every domain.

Step 1 — mint an org-less account, one call, no verification

mutation { register(input: {
  email: "probe@example.test", password: "Probe1234",
  first_name: "P", last_name: "Q"
}) { access_token user { roles { name } client_org_id } } }

→ user.roles: ["patient"]   user.client_org_id: null

Step 2 — read across tenants with that token

QueryResult as this account
clinicsleaked 4 clinics across 3 organisations, with city
servicesleaked full catalogue including prices (e.g. GP Consultation ₹499)
products, rooms, cliniciansleaked every tenant's inventory and 8-clinician roster
languages, roomTypes, clinicianTypesleaked full reference data
patients, appointments, testResultsheld — correctly returned empty
reviews, getUsers, getAuditLogs, myOrgSecuritySettingsheld — correctly FORBIDDEN

Role gating and self-scoping both work correctly. What fails is specifically the catalogue-shaped queries that scope tenancy with user.client_org_id ? {…} : {} and carry no @Auth() — a pattern written for platform admins that a public registration endpoint now satisfies for anyone.

The frontend compounds it

Two localStorage writes and a reload grant a full, forged super_admin client-side session — a mock_-prefixed token is trusted wholesale, and a failed session-check falls back to the cached (and therefore forgeable) user rather than logging out. The backend still rejects the resulting API calls, but every admin route renders, and any surviving mock fallback fills it with data that looks real.

Why 602 green tests missed a live data leak

Every backend spec replaces PostgreSQL with a mock and asserts the shape of the filter object it was handed — never whether that filter, run against a real database, actually isolates anything.

Highest-leverage fix

One integration suite: a real Postgres, two seeded organisations, and a matrix of 8 caller archetypes × every domain, asserting own-org read succeeds and cross-org read returns empty. This single suite would have caught the leak above, the two patient-scoping gaps, and the dead test-result linkage — together — the day they were introduced.

05

Competitive position & recommendations

Built for the Indian market, but benchmarked internally against a UK product. The real competitive set is Practo, Eka Care, and Bajaj Finserv Health, with Cliniko/Jane/SimplePractice as the quality bar and Zocdoc/NexHealth/Phreesia as the access-layer reference. Confirm current vendor feature sets independently — this reflects general market positioning, not a sourced snapshot.

The scheduling engine is genuinely competitive — availability templates, blocks, real-time slot updates, multi-tenant from the ground up. The product is one layer short of a system of record — no clinical notes, no prescriptions, no ABDM/ABHA. The India-specific gaps are the cheap ones — they attach to infrastructure that already exists.

1High impact, low effort, distinctly Indian — next quarter

  • WhatsApp as a notification provider. Highest ROI in this audit — the pluggable provider registry and per-org encrypted credentials already exist for MSG91/Gupshup/Twilio; this is the same shape.
  • Appointment-reminder scheduler. BullMQ and Redis are already provisioned; this is the missing piece that makes WhatsApp actually reduce no-shows.
  • Deposits at booking. Razorpay is already integrated — the most direct no-show lever available.
  • Waitlist with auto-fill on cancellation, using the existing slot-availability engine.
  • Review submission. The review flywheel is missing its first step — there is currently no way for a patient to submit one at all.
  • GST-compliant patient invoices — a statutory requirement, currently impossible for patient (Razorpay) payments.

2The moat — 2–3 quarters

  • Clinical MVP: consultation notes, diagnosis coding, structured e-prescriptions. The patient detail page already has the UI shell, driven by nothing.
  • ABDM / ABHA integration. Long certification lead time — start the paperwork now regardless of build sequencing.
  • Real teleconsultation behind the existing, unimplemented video route.
  • Make RBAC real. Currently a hard procurement blocker dressed as a shipped feature.

3Parity & platform — ongoing

  • Digital intake, kiosk check-in, and patient journey — turning two mock-only pages into a real domain.
  • Insurance / TPA and cashless workflows for mid-market clinics.
  • True slot-capacity utilisation, replacing the documented completion-rate proxy.
  • Plan-tier entitlement enforcement, observability, and the DPDP Act 2023 compliance programme.
